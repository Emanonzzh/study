# 项目二 · Agent 开发学习路线（以销售经营分析系统为载体）

> 触发：2026-09-14，「我想从这个项目入手能够增加我对 agent 开发的了解」。
> 本文回答：**为什么你学完 RS 项目还是觉得"什么都不懂"，以及这个项目怎样设计才能真的学会 Agent 开发。**

---

## 一、先点破一个冲突（必须先解决）

我在《框架评审》里推荐的架构是：**确定性 DAG + LLM 只在"解析需求"和"叙述结论"两个节点**。

这个架构对企业是**对的**，但它教给你的是 **"什么时候不该用 Agent"**。
如果你照着它做完整套项目，你会学会：SQL、指标口径、分解数学、评测、工程化 —— **但 Agent 的核心机制你一个都没亲手实现过**。

所以两个目标要分开满足：

| 目标 | 需要的形态 | 在哪条线 |
|---|---|---|
| 求职作品（可验证、可复现、能讲取舍） | 确定性 DAG + 严格评测 | **主线** |
| 学 Agent 开发（亲手实现每个机制） | 多种 Agent 范式的实现与对比实验 | **实验线 `agent_lab/`** |

**两条线共用同一套工具函数、同一个数据库、同一套评测集。** 这样实验线的产物天然是主线的一部分，不是玩具。

## 二、学 Agent 开发的真实门槛在哪（为什么你"学完了还是不懂"）

你的 RS 项目里是：
```python
agent = create_agent(model, tools)   # 一行
```
这一行背后，框架替你做了：prompt 组装、工具 schema 注入、多轮循环、消息历史维护、停止条件、错误回传。
**你只是调用了它，没有实现它** —— 所以"学完了 RAG、Agent、FastAPI 还是什么都不懂"。

真正的 Agent 开发能力，是这 12 个机制**你都亲手处理过至少一次**：

| # | 机制 | "只会调框架"的表现 | "真会"的表现 |
|---|---|---|---|
| 1 | **工具定义** | 写个 `@tool` 装饰器就完了 | 能设计**工具粒度**：为什么"查指标"要拆成 5 个函数而不是 1 个万能函数；参数校验失败时怎么把错误**当作 observation 回传给模型**让它自己改 |
| 2 | **循环与停止条件** | 靠框架默认 max_iterations | 能自己实现循环，并处理：步数上限、token 预算、**重复调用同一工具检测**（死循环）、超时 |
| 3 | **上下文工程** | 把全部历史塞进 prompt | 知道每步该塞什么：全部 observation 会爆 token，只塞最近 N 步会丢目标 → 会做**摘要压缩 + 关键结果固定保留** |
| 4 | **失败模式识别** | 报错就重试 | 能列出模型的典型失败：工具名幻觉、参数类型错、忘记原始目标、过早收敛、把观察结果复述当结论 → 每个都有对策 |
| 5 | **规划** | 让模型"自己想办法" | 会实现 Plan-and-Execute：先出结构化计划（Pydantic 校验）→ 逐步执行 → 计划与结果偏离时**重规划** |
| 6 | **反思/自我纠错** | 无脑 while 循环重试 | 知道**"只纠错一次"**比"无限重试"更好（原项目就是只纠错一次），并能解释为什么（成本 + 振荡） |
| 7 | **状态与记忆** | 用框架的 checkpointer | 分得清**会话内短期记忆**、**跨会话长期记忆**、**任务状态**（LangGraph state）三者的区别与存储位置 |
| 8 | **多智能体** | 起 3 个 agent 互相喊话 | 知道 Supervisor 路由 vs 顺序管道 vs 并行 fan-out 的适用边界，以及**为什么多 Agent 常常不如一个 Agent + 更多工具** |
| 9 | **HITL 人工介入** | 没做过 | 能实现"执行前暂停等审批、审批后从中断点恢复"（LangGraph `interrupt` / 状态持久化），并设计超时与拒绝路径 |
| 10 | **可观测性** | 打印日志 | 每步记录：输入摘要、选中工具、参数、观察、耗时、token、成本 → 能回答"这次为什么答错"和"哪一步最贵" |
| 11 | **评测** | 看几个例子觉得"还行" | 知道 Agent 评测要分**过程（轨迹对不对）**和**结果（结论对不对）**，并有回归集 |
| 12 | **安全与成本** | 没考虑 | 工具权限最小化（只读）、注入防护、单次任务 token 上限与熔断（原项目的四层 SQL 防护就是范本） |

> **这 12 条，就是你这次要补的短板清单。** 每一条都要有"我亲手写过并踩过坑"的记录。

## 三、双线设计（同一个仓库）

```
ai-commerce-intelligence-platform/
├── analysis/                 # 主线：分析纯函数层（Phase 2）
│   ├── metrics.py            #   指标口径
│   ├── contribution.py       #   量价结构分解（可加总断言）
│   ├── anomaly.py            #   异常检测（日历校正 + 最小支持度 + FDR）
│   └── attribution.py        #   逐维下钻归因
│
├── agent_lab/                # ★ 实验线：Agent 范式实验室（本项目新增）
│   ├── tools.py              #   统一的工具集（纯函数，主线和实验线共用）
│   ├── p0_single_call.py     #   范式 0：单轮 Function Calling（基线）
│   ├── p1_react.py           #   范式 1：手写 ReAct 循环（不用框架）★第一个里程碑
│   ├── p2_plan_execute.py    #   范式 2：先规划后执行
│   ├── p3_reflection.py      #   范式 3：反思与自我纠错（一次 vs 无限，对比实验）
│   ├── p4_supervisor.py      #   范式 4：Supervisor 多 Agent（GPT 框架建议的那种）
│   ├── p5_deterministic.py   #   范式 5：确定性 DAG + 2 个 LLM 节点（生产形态）
│   ├── trace.py              #   统一轨迹记录（步数/工具/参数/token/耗时）
│   └── evaluate.py           #   五范式跑同一套题 → 对比报告
│
└── docs/eval/agent_paradigm_report.md   # ★ 产出：范式对比 A/B 报告（简历直接引用）
```

### 为什么"范式对比"是学 Agent 最好的方式

因为它把"我用了 LangGraph"变成 **"我用数据证明了什么时候该用哪种编排"**：

> "同一套 25 条业务问题，我实现了 5 种编排范式并评测：
> 单轮调用结论正确率 52%；手写 ReAct 68% 但平均 6.3 步、成本 4.1 倍；
> Supervisor 多 Agent 71% 但失败模式集中在'路由错维度'；
> 确定性 DAG + 2 LLM 节点 88% 且成本最低。
> **结论：分析类任务里，把确定性计算交给代码、只在语义理解与表达用模型，准确率和成本同时最优。**"

这段话是 Agent 岗位面试里最有分量的回答之一 —— 因为它展示的是**判断力**，而不是 API 熟练度。
而且**你手上已经有现成范例**：原作者的 `agent_core/eval/ab_routing_report.md`（规则路由 vs LLM 路由的 A/B）就是这种写法的模板，你可以直接沿用它的报告格式。

## 四、五个范式（按实现难度排序，逐个手写）

| 范式 | 实现要点 | 你会亲手处理的机制 | 预期失败模式（要记录！） |
|---|---|---|---|
| **P0 单轮调用** | 一次请求，模型直接选工具（或无工具直接答） | 工具 schema 注入、JSON Mode | 多步问题必然失败（如"11月为什么量增价减"要 3 步） |
| **P1 手写 ReAct** ★ | **不用任何框架**，自己实现 `thought → action → observation` 循环 | 循环、停止条件、错误回传、上下文累积、trace | 工具名幻觉、参数错、重复调用、把观察复述当结论、步数爆炸 |
| **P2 Plan-Execute** | 先出结构化计划（Pydantic）再逐步执行 | 任务分解、计划校验、执行与计划偏离 | 计划里的工具不存在、依赖顺序错、计划过粗 |
| **P3 反思** | 结果自检 → 修正 → **只允许一次** | 自我评估、修正触发条件、成本控制 | 越改越错（振荡）、把对的改错 |
| **P4 Supervisor 多 Agent** | 一个路由 Agent + 3 个专职 Agent（分析/异常/报告） | 多智能体路由、handoff、结果聚合 | **路由错维度**、Agent 之间来回踢皮球、上下文在传递中丢失 |
| **P5 确定性 DAG** | LangGraph 显式节点，LLM 只在 plan/narrate | 状态图、条件边、确定性复现 | 计划解析失败（JSON 不合法） |

**P1 是第一个里程碑**：因为手写过一遍 ReAct，你再看 LangGraph 的 `create_agent` 就知道它到底替你做了什么 —— 这是"从会调到会做"的分水岭。

## 五、统一评测：5 个范式跑同一套题

必须**同一套题、同一套工具、同一套判定**，否则对比没有意义。

### 评测集（三档难度）
| 档 | 题量 | 例 | 正确答案判定方式 |
|---|---|---|---|
| 单步取数 | 10 | "11 月的实付额是多少？" | 数字与 SQL 复算一致（**机器判定**） |
| 多步分析 | 10 | "11 月单量涨了但收入没涨，为什么？" | 必须命中"量效应/价效应/结构效应"三项且数字对账（**机器判定**） |
| 开放诊断 | 5 | "这个月经营上有什么值得关注的问题？" | 是否命中标注的真实事件（**人工 + 事件命中率**） |

### 统一指标（每个范式都要跑出这 6 个数）
| 指标 | 说明 |
|---|---|
| **结论正确率** | 数字对账通过 + 必要条件命中 |
| **数字对账通过率** | 报告/回答里的每个数字能否在 DB 复算出来（**防幻觉硬指标**） |
| **平均步数** | 循环类范式的核心成本指标 |
| **token / 成本** | 按 DeepSeek 实际计费算，折算成"每次分析多少钱" |
| **P50 / P95 延迟** | 交互体验 |
| **失败模式分布** | 幻觉工具 / 参数错 / 跑偏 / 步数爆炸 / 过早收敛 各占多少 |

> 最后一行是**最容易被忽略、也最能体现深度**的：能说清"我的 Agent 主要死在哪种失败模式上，我怎么修的"，比"我的 Agent 准确率 90%"更可信。

## 七、必须手写的练习（配合你已有的手写习惯）

1. **不看任何框架**，手写一个 ReAct 循环（≤150 行），工具只有 2 个（查指标 / 看趋势），能答"11 月实付额多少"；
2. 给它加**死循环检测**（同一工具同一参数连续调用 2 次就中断）——记录模型在什么情况下会死循环；
3. 加**token 预算**：超过预算强制收敛，观察准确率怎么掉；
4. 把 `tool` 的参数故意改成错的类型，看模型能否根据错误信息自我修正（**这是错误回传的价值验证**）；
5. 用 LangGraph 重写同一个循环，逐行对照"框架替你做了什么"；
6. 手工构造 10 条评测题，跑 P0 vs P1，亲手看到差距。

> 做完 1~4，你对 Agent 的理解会**超过 90% 只会调 LangChain 的人**。
