# 项目二框架评审：基于 Agent 的智能销售数据分析与经营报告系统
## —— 对企业化架构设计的一份技术判断与修正方案

> 背景：2026-09-14，拿到一份"GPT 给的框架"（Supervisor + 3 Agent + 数据清洗→指标→分析→异常→报告 → FastAPI/MySQL/Nginx/Docker）。
> 本文回答三个问题：**这个框架哪里对、哪里会做成玩具、以及在你已经跑通 `ai-commerce-intelligence-platform` 的前提下到底该怎么做。**

---

## 〇、一句话结论

**方向选对了**（销售经营分析比遥感问答更贴 JD，且能补上你最缺的"完整系统架构 + 业务流程"），
**但这套框架本身有三个会导致"看起来像企业级、一戳就破"的结构性问题**：

1. **"3 个 Agent" 是花架子** —— 数据分析和异常分析本质是确定性代码，包成 Agent 只增加成本、延迟和不确定性；
2. **异常发现与归因没有方法论** —— 只有"LLM 解释原因"的图，没有可验证的统计判据和分解数学；
3. **没有 ground truth 和数字对账** —— 这正是你上个项目被说"玩具"的根因，换个业务场景不会自动消失。

还有一个他没提到的现实：**你克隆并跑通的那个项目已经覆盖了这份框架约 70% 的内容**，所以真正值得你投入的增量只有 3 块（见第二节）。

## 三、修正一：把"Supervisor + 3 Agent"换成"确定性 DAG + 两个 LLM 节点"

### 问题在哪

GPT 的架构是：Supervisor Agent 判断 8 个步骤 → 调度数据分析/异常分析/报告 3 个 Agent。
**这个设计的问题不是"不够高级"，而是"把确定性的事情交给了不确定的模型"：**

- 销售额、环比、排名、贡献度分解 —— 这些都是**有唯一正确答案的计算**，用 LLM 决定"要不要算、怎么算"只会引入不确定性；
- 每多一个 Agent 节点 = 多一次 LLM 往返 = 多一份延迟、token 成本和失败概率；
- 更致命的是**不可测**：模型这次规划 6 步、下次规划 4 步，你的评测集无法稳定断言。

**而且你的项目里已经有现成的反证**：原作者做了"确定性规则路由 vs LLM 自主路由"的 A/B 实验，规则路由在 curated 集上 100/100、留出集 60%，并且**如实披露**（`agent_core/eval/ab_routing_report.md`）。
→ 也就是说：**"让 Supervisor 自主判断 8 步"这个建议，恰好和这个项目已经用数据证明的结论相反。** 面试时你如果照 GPT 的做，等于放弃了手上最有力的论据。

### 修正后的架构

```
                    Streamlit 前端（复用现有）
                            │
                    FastAPI（复用现有，加 2~3 个接口）
                            │
              ┌─────────────▼─────────────┐
              │  Analysis Orchestrator    │  ← LangGraph 确定性 DAG
              └─────────────┬─────────────┘
                            │
   ①plan(LLM，唯一必选) ────┤  只做一件事：把自然语言 → 结构化分析计划
                            │  输出：{期间, 维度, 指标口径, 对比基线}（Pydantic 校验）
                            ▼
   ②取数与指标(纯代码)  ── 并行 ──  ③异常检测(统计)   ④知识检索(RAG，口径/政策)
                            │            │                  │
                            └────────────┴──────────────────┘
                                         ▼
   ⑤归因下钻(纯代码)：总量 → 区域 → 产品 → 客户 → 时间，逐层分解
                                         ▼
   ⑥narrate(LLM，第二个也是最后一个 LLM 节点)：只把**已算好的结构化结果**写成结论/建议
                                         ▼
   ⑦模板渲染(纯代码)：Jinja2 → Markdown / PDF / Excel + **数字对账校验**
```

**LLM 只在 ①plan 和 ⑥narrate 两个节点。** 中间全是纯函数 —— 可单测、可复现、可断言、零 token。

### 为什么这个更好（面试话术）

> "分析类系统里 90% 的步骤有唯一正确答案，我把它做成确定性 DAG，只在'理解问题'和'表达结论'两处用 LLM。
> 这样做的收益是：同样的输入必然得到同样的数字（可复现）、每一步都能单测、单次分析的成本和延迟从 O(Agent步数) 降到 O(2)。
> 我也做了对照：如果让模型自主决定分析步骤，它有时会漏掉'产品维度'下钻，结论就不可比了 —— 分析系统的结论必须是可比的。"

## 四、修正二：异常发现要有统计判据（不能"LLM 觉得降了 18.6% 就是异常"）

GPT 这点方向对了（先发现异常、再调工具拿数据、最后 LLM 解释），但**没给判据**，落地就会变成"拍脑袋定阈值"。

### 分层检测（关键：只看总量会漏掉结构性异常）

总量持平但华东崩了 30%、被华南增长掩盖 —— 这类异常**只有在维度层才看得见**。检测要分层跑：

| 层级 | 检测对象 | 典型异常 |
|---|---|---|
| L1 总量 | 期间销售额/毛利率 | 整体未达目标 |
| L2 维度 | 区域 / 产品 / 渠道 / 销售员 | 单区域或单产品显著偏离 |
| L3 客户 | 大客户、客户分群（RFM 迁移） | 核心客户采购骤降 |
| L4 时间 | 日/周粒度、变点 | 8 月第 2 周起持续下滑 |

### 判据（建议按此顺序实现，越往后越"企业"）

1. **规则基线**：环比 / 同比（需 ≥18 个月数据）+ 目标完成率（需 targets 表）
2. **季节基线**：用 18~24 个月数据估月份季节因子 + 周内效应（数据里有 `weekday`/`order_hour`，天然支持），算"季节调整后偏离"
3. **稳健统计**：MAD 稳健 z 分数（`0.6745 * (x − median) / MAD`，|z| > 3.5），**比均值±3σ 更抗离群**（否则异常点会把自己的阈值撑大）
4. **变点检测**：CUSUM 或 PELT（`ruptures` 库）识别"从某天起持续下滑"，比单点阈值更符合业务语义（"趋势型异常"）
5. **误报控制（这一段最能体现你懂工程）**：
   - **最小支持度门槛**：订单数 < N 或金额 < 阈值时不做统计判定（否则长尾小类天天"异常"）
   - **多重比较校正**：对几百个"区域×产品"组合同时检测，必然产生大量假阳性 → 用 Benjamini-Hochberg 控制 FDR，或对维度组合做最小金额筛选
   - **异常分级**：告警/关注/正常，而不是二值

### 必做：给异常检测做 ground truth

**在造数据时就注入已知异常**，并记录清单（含少量"伪异常"作为噪声）。这样才能算出：

> 异常检测：召回 10/12、误报 2（F1 = 0.87）—— **这句话的含金量高于整个多 Agent 架构。**

## 五、修正三：归因要用"量-价-结构分解"，这是整个项目的技术天花板

GPT 的"归因"是：华东降 18.6% → 看产品 → 看客户 → 看时间 → LLM 总结。
**下钻路径是对的，但缺了数学内核**：下钻只是"找到哪个维度降了"，而企业要的是**"它贡献了多少个百分点"**。

### 三个可精确加总的分解（都可写成断言测试）

**① 量价分解（单品/单维度）**

```
ΔR_i = (q1_i − q0_i)·p0_i      ← 量效应
     + q0_i·(p1_i − p0_i)      ← 价效应
     + (q1_i − q0_i)·(p1_i − p0_i)  ← 交叉项
Σ_i ΔR_i = ΔR_total   （必须精确成立 → 写单元测试断言，误差 < 1e-6）
```

**② 贡献度（回答"是谁造成的"）**

```
产品A 对总下滑的贡献 = ΔR_A / |ΔR_total| = 3.1 个百分点
→ 直接生成瀑布图（waterfall）：总变化向下拆到各维度贡献
```

**③ 结构效应 / mix（进阶，区分"卖得少了" vs "卖的东西变便宜了"）**

```
p̄ = Σ w_i·p_i ,  w_i = q_i / Σq
Δp̄ = Σ(w1_i − w0_i)·p0_i   ← 结构效应（高毛利产品占比下降）
    + Σ w0_i·(p1_i − p0_i)  ← 纯价效应（降价/折扣变深）
平均客单价下滑时，这两者的经营含义完全相反（是产品结构劣化，还是单纯降价换量？）
```

**④ 客户侧拆分（同样是精确分区）**

```
ΔR = 留存客户贡献变化 + 新增客户贡献 − 流失客户贡献
集中度：CR5 / HHI 变化 → "收入越来越依赖少数大客户"是可量化的风险信号
```

> 面试价值：会讲"量价结构三因素分解 + 瀑布图"的人，比会讲"我用了多 Agent"的人少得多，而且**它是可验证的**——分解加总回不到总变化，说明你算错了。这是"真做过分析"和"套壳调用 LLM"的分水岭。

## 六、修正四：报告生成的关键不是模板，是"数字不许由 LLM 产生"

GPT 说报告输出 Markdown/PDF/Excel —— 对，但没提**防幻觉**，而这是报告类系统最大的坑。

### 正确做法

1. **报告结构由数据反推**：先定报告的字段清单（概览/区域/产品/异常/归因/建议），**这个清单就是分析层的输出契约**（MVP 阶段最实用的一条：报告是需求的载体）；
2. **数字全部来自工具结果**：报告用 **Jinja2 模板 + 结构化 JSON** 渲染，模板里只有占位符；
3. **LLM 只写"结论与建议"两段自然语言**，且输入是已算好的 JSON（不给它原始表，避免它自己算）；
4. **发布前数字对账（必做）**：正则抽取报告里所有数字 → 与分析结果 JSON / 数据库重算结果比对 → 不一致就**拒绝发布并告警**。
   > 评测指标：**报告数字对账通过率 100%**。这句话比"用 LLM 生成了报告"有用一百倍。
5. **建议要受知识库约束**：建议不得违反价格政策/折扣上限（RAG 提供政策原文 + 引用来源），报告里标注"依据：《2026 销售目标管理办法》第 3.2 条"。

## 七、修正五：RAG 的三个正确用途（不是又一次"文档问答"）

你上个项目的教训是"为了用 RAG 而用 RAG"。在这个系统里，RAG 有明确的活干，但要限定范围：

| 用途 | 具体作用 | 不这么做会怎样 |
|---|---|---|
| ① **口径解析** | "销售额"取 `order_amount` 还是 `payment_amount`？退款要不要扣？→ 直接约束 SQL 生成 | 同一个问题两次问出两个数 |
| ② **规则/阈值依据** | 《销售目标管理办法》规定完成率 <95% 触发预警；价格政策规定折扣上限 | 阈值变成硬编码魔法数字，改一次要发版 |
| ③ **建议的政策约束** | 生成建议时检索政策，避免"建议打折促销"违反价格政策 | 报告给出违规建议 |

> 更好的做法：**阈值、目标、KPI 口径做成结构化规则表（可配置 + 版本化）**，RAG 只负责"口径说明与政策依据的引用"。
> 这样报告能回答"这个结论的依据是什么"——这是经营报告被信任的前提。

## 八、数据设计（GPT 说得对的部分 + 必须补的三点）

### 表设计（在它的 5 张表基础上补 2 张）

| 表 | 关键字段 | 补它的用途 |
|---|---|---|
| `sales`（明细，5 万行） | 日期(含小时)、订单ID、客户ID、产品ID、区域、销售员、数量、销售额、成本 | 主表 |
| `products` | 品类、成本、标价、价格档 | 算毛利、量价分解 |
| `customers` | 等级、所属区域、负责销售员、首单日期 | 客户维度下钻 |
| `regions` / `salespersons` | 名称、层级、上级区域 | 组织维度下钻 |
| **`targets`** | 月度目标（区域/产品/销售员） | **目标完成率预警**（GPT 漏了，但这是"经营"的核心） |
| **`kpi_definitions`** | KPI 口径、公式、生效版本 | **口径可审计**（报告记录用了哪版口径） |

### 必须补的三点

1. **时间跨度 ≥ 18~24 个月**：只有几个月做不了同比，季节基线也没法估 —— 这是很多"销售分析项目"一看就假的破绽；
2. **注入已知异常并留标注清单**：趋势型（某客户 8 月起采购降 60%）、脉冲型（某区域单日暴增，促销或刷单）、结构型（高毛利产品占比下降）——**没有 ground truth 就无法证明异常检测有效**；
3. **上传/导入要"企业化"**：schema 契约校验 → 文件哈希 + 批次号幂等导入（重复上传不重复计数）→ 行数/金额对账 → 支持按批次回滚。
   > 企业里没人会"随手传个 CSV 就建表"，这块做扎实了是加分项，做浅了就是 demo 感。

> 数据量口径：5 万行对 MySQL 是**小数据**，简历里**不要写"大数据"**。若想练性能，另做 100 万行压测并说明索引/聚合的差异。

## 九、修正六：不要 Celery；但权限和审计要做

| GPT 的建议 | 我的判断 |
|---|---|
