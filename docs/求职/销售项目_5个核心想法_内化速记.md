## ① 量价分解：把一个变化拆成"卖得更多"和"卖得更贵"

### 先手算一遍（看懂这个就懂 80%）

> 上月：卖 **100 单**，每单 **100 元** → 10000 元
> 本月：卖 **150 单**，每单 **80 元** → 12000 元
> 总变化：**+2000 元**。这 2000 是哪来的？
>
> | 拆解 | 算法 | 金额 |
> |---|---|---|
> | **量效应**（多卖 50 单，按老价格算） | 50 × 100 | **+5000** |
> | **价效应**（每单便宜 20，按老单量算） | 100 × (−20) | **−2000** |
> | **交互项**（多卖的那 50 单也是便宜价卖的） | 50 × (−20) | **−1000** |
> | **合计** | 5000 − 2000 − 1000 | **= 2000** ✅ |
>
> **三项加起来刚好等于总变化** —— 这就是"精确加总"。

### 项目里的真实数字（10 月 → 11 月）

| | 10 月 | 11 月 | 变化 |
|---|---|---|---|
| 订单数 | 8,859 | 10,910 | 多卖 2,051 单 |
| 客单价 | 985.23 | 927.37 | 每单便宜 57.86 元 |
| 销售额 | 8,728,115 | 10,117,593 | **+139.5 万** |

拆解：量效应 **+202.07 万** + 价效应 **−51.26 万** + 交互项 **−11.87 万** = **+138.9 万** ✅

### 一句话结论（这才是老板要的洞察）

> **涨是靠"多卖单"撑起来的，客单价在拖后腿 —— 这叫「以量补价」，增长质量要打问号。**

### 可能被追问

- **"为什么三项而不是两项？"** → 两因子是近似、无法验证；三因子才能**精确加总回总变化**，于是能写成断言（我实测闭合 `0.0`）。
- **"交互项是什么？"** → 量价同时变化产生的交叉影响。省了它，三项之和就不等于总变化。

## ② 异常检测：判断"这个波动是不是不正常"

三个关键点，每个都能用大白话讲：

### 1. 不能只看"降了 20% 就算异常"

因为**周六本来就比周一高 40%**。所以基线要拿「**同一个星期几**」的历史值比（周六跟周六比）。

> **我的真实教训**：第一版用"3 天窗口比中位数 + 30% 阈值"跑真实数据，检出 **175 个"异常"，全是误报** ——
> 因为拿 3 天窗口比，等于拿周六比周一。改成整周对整周 + 同星期几基线后，降到 22 个。

### 2. 用中位数，不用平均值

一个异常点会把平均值拉高，**反而把自己藏起来**。中位数抗这个（术语叫"稳健统计"，用 MAD 衡量偏离）。

### 3. 订单太少的切片不判

项目里有个渠道整年只有 **3 单**，它随便波动都是"100% 异常"。所以要设门槛：**订单数 < 30 的切片不参与判定**。

### 可能被追问

- **"为什么叫 MAD？"** → 绝对中位差，衡量"典型偏离幅度"。乘 1.4826 就是稳健标准差估计。**关键好处：异常点无法把自己的阈值抬高。**
- **"门槛设多少合适？"** → 我做过扫描实验：10/30/50 指标几乎不变，**提到 80 才开始漏检**（日单量不足 80 的平台被整体挡掉）→ 门槛过高会伤查全率。

## ③ 评测：我怎么证明"检测得准"

### 难点

**真实数据没有标准答案**。元旦销售额暴涨 3 倍 —— 这算该被检出的异常吗？没人标注，就算不出准确率。

### 我的做法（三步）

1. **故意注入 6 个已知异常**：把某平台某两周的销售额打 4 折、某天打 3.5 倍……记下清单 = **标准答案**
2. 让检测器去跑 → **查全 100%（6/6 全找出来）**
3. **差分**：真实数据本身有元旦暴涨这类真实事件，直接比对会把它们冤成误报 → 用「**注入表检出的 − 干净表检出的**」，剩下的才是注入引起的
   - 结果：**无关误报 0** —— 报出来的每一条都能对上某个注入事件

### 可能被追问

- **"差分是不是在作弊？"** → 不是。它只是把"真实业务事件"这个**噪声地板**剔掉，衡量的是"注入引起的异常有没有被抓到"。而且我**同时报了严格口径**（P=35.29%）做对照，没有只挑好看的数字。
- **"P 只有 54% 是不是很差？"** → 那 5 个"误报"我逐条归因过，**全部落在注入事件区间内或前后几天**——它们是持续型异常的「进入点 / 内部点 / 恢复点」。**是评测方法（一对一匹配）太严，不是检测器错了。** 加"事件化后处理"（间隔 ≤7 天的检出合并成一个事件）后 P 就上去了。

## ④ 数字对账：防止报告里出现假数字

报告类系统最大的坑是**模型编数字**。三道防线：

1. **数字全部由代码算好**，模板里只有占位符；模型只写**不含数字**的自然语言
2. **文本级对账**：报告里**每个数字抽出来**核对来源 → **88 个数字，0 违规**
3. **数据库级对账**：关键指标**重新从数据库算一遍** → **11 项全部一致（Δ=0.0）**

### 最加分的一步：给对账器本身做自测

> **"报告 0 违规"本身是不可信的 —— 万一是我的对账器太宽松（或坏了）呢？"**
> 所以故意塞一个假数字 `999,999.99`，看它抓不抓得到 → **✅ 抓到了**。
> 这才叫「测试测试本身」。

### 可能被追问

- **"对账器自己出过 bug 吗？"** → 出过 3 个：① 正则把逗号当边界，`-512,555.14` 被切成 `555.14`；② 百分数口径混用（源里 `55.9` 已是百分数，我按 ×100 找）；③ 派生值（环比、异常数）没进"授权数字清单"。**修完 100% 通过** —— 这段很能讲，说明我真在调试而不是套模板。

## ⑤ Agent 部分：手写 ReAct 循环（不依赖框架）

### 什么是 ReAct

就是"**想 → 做 → 看结果 → 再想**"的循环：

```
Thought（我想查什么）
Action（调用哪个工具）+ Action Input（参数）
Observation（工具返回的结果）
…… 重复直到能回答 ……
Final Answer
```

### 我亲手实现的东西

| 机制 | 我的做法 |
|---|---|
| 停止条件 | 步数上限 8 / token 预算 24000 / 单步超时 60 秒 |
| **重复动作检测** | 同一工具同一参数连续调用 → 拦截（防死循环） |
| **错误回传** | 工具报错**不直接抛异常**，而是作为 Observation 喂回模型 → 让它**读懂错误再修正** |
| 上下文控制 | Observation 超过 1800 字符就截断（防 token 爆炸） |
| 可观测性 | 每步记录 thought / action / 参数 / 耗时 / token |

### 最有价值的一个坑（面试重点）

> **死循环检测误伤了"合法重试"**：工具报"数据库超时，可原样重试"后，模型原样重试 → 被我的重复检测拦下 → 模型最后只能放弃。
> **是我的机制错了，不是模型的错。** 状态从"计数"改成 `{count, last_error}`，**上一次以工具错误收场时放行一次重试** → 模型成功恢复，耗时从 24.8s 降到 3.1s。

### 可能被追问

- **"为什么手写不用 LangGraph？"** → 先搞清框架替我做了什么（prompt 组装、工具 schema 注入、多轮循环、消息历史、停止条件、错误回传），再决定用不用它。**生产上我还是会选框架，但选型判断得建立在自己实现过的基础上。**
