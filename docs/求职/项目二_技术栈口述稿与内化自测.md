# Part 2 · 技术栈口述稿（分层，每层都带"为什么"和"我踩的坑"）

> 面试时技术栈不是背清单，而是讲**选择**：为什么用它、替代方案是什么、踩了什么坑。
> 下面每一层的"坑"都是真实发生过的，可以直接讲。

## 2.1 数据层 · MySQL 8.4.9 + 102,287 行真实订单

**是什么**：16 字段订单明细（订单号/客户/商品/金额/优惠/退款/时间/平台/渠道），把仓库自带的 16MB CSV 用 `LOAD DATA INFILE` 导入 MySQL，`ai_commerce_intelligence_platform.orders`。

**为什么这么选**
- 真实数据（不是造的），字段有业务含义，直接决定分析维度；
- `LOAD DATA` 而不是逐行 INSERT：102,287 行 **2.3 秒**导完，这是 MySQL 的标准批量导入姿势；
- 保留 MySQL 而不是换 PG：原项目后端硬编码 `mysql+pymysql`，替换成本大于收益（**技术选型要考虑存量约束**）。

**替代方案 / 取舍**
- SQLite：更快起步（我本机就有个 102,287 行的 SQLite 演示库），但没有 `LOAD DATA`、类型/索引能力弱，且和线上形态不一致；
- PostgreSQL：pgvector 生态更好，但对本项目当前阶段无收益。

**我踩的坑（可讲）**
1. Windows 下没有管理员权限 → 装不了 MySQL Installer，改用**官方便携版 ZIP**（`mysqld --initialize-insecure` + 自定义 `my.ini`）绕开；
2. **`secure_file_priv`**：`LOAD DATA` 只能读指定目录，原项目 SQL 里写的是容器路径 `/var/lib/mysql-files/`，Windows 上必须改配置 + 改路径（我另存了一份 `02_import_data.windows.sql`，原文件不动）；
3. **`\P` 陷阱**：用 `mysql -e "source F:\Python\..."` 时反斜杠被客户端当成命令，报 `Unknown command '\P'` → 路径必须用正斜杠；
4. **`skip-name-resolve` 陷阱**：开了它以后 `root@localhost` 匹配不上 `127.0.0.1` 的 TCP 连接，报 `ERROR 1130`；
5. PyMySQL 连 MySQL 8 的 `caching_sha2_password` 需要 `cryptography` 包，venv 里没有 → 补装。

**数据能力边界（主动说，别等被问）**
- ❌ **没有成本字段** → 毛利率/利润一律算不了；
- ❌ **只有 2025 一年** → 同比做不了；
- ❌ **没有区域、销售员字段** → 这两个维度不存在；
- ⚠️ 平均 1.31 单/人 → 客户维度信息量弱，"大客户流失归因"不成立；
- ✅ 一单一品（订单号唯一）→ 所以量价分解的"量"用订单数、"价"用客单价，**可以精确加总**。

> 这段"主动交代数据边界"是加分项：它证明你**真的读过数据**，而不是套模板。

## 2.2 分析层 · 纯函数 + 量价结构分解

**是什么**：`Revenue = 订单数 N × 客单价 AOV`，对两个期间做三因子分解：

```
ΔR = (N₁−N₀)·AOV₀        量效应
   + N₀·(AOV₁−AOV₀)      价效应
   + (N₁−N₀)·(AOV₁−AOV₀) 交互项
```

**为什么这是项目的技术内核**
- 它回答的不是"降了多少"，而是**"谁造成的、各占多少"**（贡献度、瀑布图）；
- **可验证**：三项加总必须精确等于 ΔR，我把它做成断言（实测 `check = 0.0`）。"结论可验证"是分析类系统被信任的前提。

**真实跑出来的结论（可直接讲）**
> 2025 年 10 月 → 11 月，销售额 872.8 万 → 1011.8 万（+15.92%）。
> 其中**量效应 +202.07 万、价效应 −51.26 万**、交互 −11.87 万。
> 也就是：增长完全靠单量（8,859 → 10,910 单），客单价从 985.23 降到 927.37 在拖后腿——典型的"以量补价"。
> 分平台看，微信公众号量效应 +112.9 万但价效应 −27.5 万，APP 量效应 +96.8 万、价效应 −18.5 万，**公众号的价格压力更大**。

**替代方案 / 取舍**
- 让 LLM 直接看数据说原因：不可复现、无法对账、数字会错；
- 只做同比/环比：说得出"降了 18%"，说不出"谁造成的"。

## 2.3 Agent 层 · 手写 ReAct（不用框架）+ 4 个工具

**是什么**：**不用 LangChain**，原生 HTTP 调 DeepSeek，自己实现经典 ReAct 文本协议循环：

```
Thought → Action → Action Input(JSON) → Observation → … → Final Answer
```

**亲手实现的机制**
| 机制 | 我的实现 |
|---|---|
| 循环与停止条件 | 步数上限 8 / token 预算 24000 / **重复动作检测** / 单步超时 |
| 上下文工程 | observation 截断 1800 字符（防 token 爆炸） |
| 错误回传 | 工具报错 → 作为 observation 回传，让模型**读懂错误再修正**，而不是盲目重试 |
| 可观测性 | 每步 thought/action/args/耗时/token 全记录，能定位"这次为什么答错" |
| 安全 | 工具只读 + 参数白名单校验（枚举/日期格式/月份范围） |

**为什么手写而不上 LangGraph**
> 因为我要先搞清楚框架替我做了什么。手写过一遍之后，再看 `create_agent` 就知道它内部是
> prompt 组装 + 工具 schema 注入 + 多轮循环 + 消息历史 + 停止条件 + 错误回传。
> 生产形态我还是会选框架（工程化更好），但**选型判断必须建立在自己实现过的基础上**。

**实测数据（真实）**
| 场景 | 步数 | tokens | 结果 |
|---|---|---|---|
| 单步取数（11 月实付额） | 2 | 1,435 | ✅ 10,117,593.28，可复算 |
| 对比两月涨跌 | 2 | 2,458 | ✅ +15.92% |
| 量价归因（为什么涨） | 2 | 2,704 | ✅ 量/价效应，数字 5/5 全部可复算 |

**防幻觉**：回答里每个数字回数据库复算，**5/5 通过，零幻觉**——因为所有数字都来自工具返回值（连环比都是工具算好的，并在返回值里写明"不要自己重算"）。

## 2.4 压测 · 主动把失败模式逼出来（这是最能讲的一页）

**为什么做**：第一轮 3 题全对、零失败——那不是 Agent 好，是**题目太简单**。我构造 6 个场景去撞边界：

| 场景 | 观察到的行为 | 我的结论 |
|---|---|---|
| 超纲外推（预测 2026 年 1 月） | 没有编造数字，给了区间 + 声明"未纳入促销/库存等变量" | ✅ 模型守住了"不编数字"，但**它没有说"我做不到预测"**，而是自己外推 → 需要产品层约束 |
| 非法参数（2025 年 13 月） | **发现工具 bug**（见下） | 工具校验不足，模型替工具擦了屁股 |
| **故障注入（模拟 DB 超时）** | **发现我的机制 bug**（见下） | 死循环检测误伤合法重试 |
| 极模糊提问（"最近生意怎么样"） | 没反问，自己假设了"最近 6 个月 + 营收/订单/客单价" | ⚠️ 应改为澄清或**显式声明假设** |
| 跨维度多步 | 主动纠正了用户的错误前提（"11 月两个平台都没下滑"） | ✅ 很好，没顺着错误前提编 |
| 重度取数（TOP10 商品逐个查趋势） | 工具不支持按维度查趋势 → **它诚实说"我做不到"并给替代方案** | ✅ 诚实；但暴露工具粒度缺口 |

### 我修掉的三个真 bug（面试重点，有细节有说服力）

**bug 1：死循环检测误伤合法重试**
- 现象：工具返回"数据库超时，可原样重试"后，模型原样重试 → **被我的重复动作检测拦下** → 模型最终只能回复"查询失败"。
- 根因：我的检测只看"参数是否相同"，没有考虑"上一次是以错误收场"。
- 修复：把签名状态从计数改为 `{count, last_error}`，**上一次以工具错误收场时放行一次重试**。
- 验证：重跑后模型成功恢复（拿到 10,910 单），`repeat_action` 消失，耗时 24.8s → 3.1s。
- **面试价值**：这体现的是"我的防护机制误伤了正常路径，我用状态而非计数来区分"——典型的工程判断。

**bug 2：日期校验太松（同一类 bug 有两处，第二处是代码评审时才发现的）**
- 现象：查"2025 年 13 月"，正则 `\d{4}-\d{2}-\d{2}` 放行，MySQL 返回空值，模型看到 `null/0 行` 自己推断"13 月不存在"。
- 根因：只校验格式，没校验**语义范围**。
- 第一次修复：加月份 01~12、年份范围校验，**让工具直接报出明确错误**。
- ⚠️ **第二处（同类，当时没发现）**：日期只校验了 `01~31`，于是 `2025-02-31`、`2025-04-31` 依然被放行。
  用 `calendar.monthrange` 按当月实际天数校验后修掉（闰年交给标准库，`2024-02-29` 正常放行）。
- **面试价值（比 bug 本身更值钱）**：修完第一处我以为这类问题结清了，实际上**只堵了同一个洞的一个分支**。
  教训：修边界 bug 时要问"这个洞还有别的形态吗"，而不是只修触发它的那个输入。

**bug 3：`/analyze` 用全局变量控制步数上限 → 并发竞态（会真的多花钱）**
- 现象：接口为了限制单次请求的步数，临时改写模块全局 `MAX_STEPS`，用完在 `finally` 里还原。
  单请求测试完全正确，但 FastAPI 的同步 `def` 接口跑在**线程池**里，两个并发请求会交错：
  ```
  请求 A: old=8 → 全局设为 3 ────────────────► 还原 8
  请求 B:            old=3 → 全局设为 10 ──────────► 还原 3（覆盖掉 A 的设置）
  ```
- 根因：**全局变量不是"配置"，是跨请求共享的可变状态**。A 请求可能按 B 设的 10 步跑满 → 多花钱；
  还原顺序一乱，后续请求还会继承到一个谁也没设过的值。
- 修复：把上限改成 `run_agent(max_steps=...)` 的**参数**沿调用链传下去，循环只读局部变量，模块常量退化为默认值。
- 验证：`tests/test_react_loop.py::test_concurrent_runs_keep_their_own_step_limit` 开三个线程
  分别要 1/3/5 步，各自跑出自己那步数且全局未被污染；
  `test_analyze_endpoint_passes_limit_as_argument` 钉住 api 与循环之间的契约（防止有人改回设全局）。
- **面试价值**：这是"能跑通"和"能并发"的分界线。诚实说法是：
  > 我原来用全局变量控制单次请求的步数，单请求没问题；做代码评审时意识到线程池下会有竞态，
  > 改成请求级参数，并补了一个三线程回归测试防止改回去。

## 2.4.1 单测 · pytest 230 项，**不需要 MySQL、不需要 LLM**

**为什么"不依赖外部环境"是硬要求**：一个必须有数据库才能跑的测试套件，在面试官机器上、
在 CI 里都是跑不起来的——那是负债不是资产。所以 `tests/conftest.py` 里有一个 autouse 夹具，
把 `pymysql.connect` 和 `urllib.request.urlopen` 换成"一调用就 AssertionError"：
任何测试不小心引入外部依赖，会**立刻响亮地失败**，而不是悄悄联网。

| 文件 | 覆盖什么 |
|---|---|
| `tests/test_decompose.py` | 分解的语义（纯量/纯价/同涨/下降）+ 恒等式随机性质 + **精度边界** |
| `tests/test_validation.py` | 月份/日期/维度/指标四层守卫 + 口径表完整性 |
| `tests/test_verify_numbers.py` | 对账器：假数字必抓、真数字不误判、**对账器自测**、`_month_range` 闰年 |
| `tests/test_react_loop.py` | 用**假 LLM** 驱动 ReAct：停止条件/死循环/报错重试/畸形输出/**并发竞态回归** |

**为了可测做的一次重构（可讲）**：`decompose` 原本是 `contribution_breakdown` 里的**嵌套函数**，
而嵌套函数在 Python 里 import 不到 → 等于不可测。为了单测把它提到了模块级。

**"测试通过"本身不是证据，除非它曾经失败过**：把修复临时还原后重跑，
结果是 **15 failed + 1 collection error**；恢复修复后 **230 passed**。
这一步（falsification）才是判断测试有没有价值的分界线——否则你只是写了 230 行安慰剂。

**一个诚实的边界（被问到要说）**：分解的加总闭合用 `round(..., 8) == 0` 判断，这在**真实数据量级**下成立；
但在极端量级（n₀=9999 且 n₁=1）下浮点相消会让绝对误差到 1e-5。相对误差始终在机器精度级（实测最坏 2.7e-10）。
我把这个边界写成了一条测试（`test_identity_precision_boundary_is_documented`）而不是假装不存在。

## 2.5 编排层 · 确定性 DAG + 两个 LLM 节点（设计决策）

**主张**：分析类任务里 90% 的步骤有唯一正确答案，不该交给模型。

```
plan(LLM ①) → 取数/指标(代码) → 异常检测(统计) → 归因下钻(代码) → narrate(LLM ②) → 模板渲染(代码)
```

**为什么**：同输入必然同结果（可复现）、每步可单测、成本从 O(步数) 降到 O(2)。
**反面证据我手上有**：原项目做过"规则路由 vs LLM 自主路由"的 A/B——规则路由 curated 集 100/100，且如实披露留出集只有 60%。**用数据证明取舍，而不是嘴上说**。

## 2.6 服务与部署层（复用现有存量系统）

| 组件 | 作用 | 说明 |
|---|---|---|
| FastAPI | 后端接口 | 存量已有 32 接口 + JWT + 限流 + 缓存 |
| Streamlit | 前端 | 存量已有 BI 看板 + AI 助手两个应用 |
| Redis | 会话 | 存量已有，未启用时降级内存（上限 1000） |
| Nginx | 统一入口 | 存量已有，`expose: 3306` 不占宿主端口 |
| Docker Compose | 编排 | 存量 7 服务（nginx/mysql/redis/backend/streamlit/ai-assistant/db-bootstrap） |
| pytest | 测试 | 存量 88 个测试；**我自己的 `agent_lab/tests/` 另有 230 项**（不依赖 MySQL/LLM，0.3s） |

**我踩的坑（Windows 环境，可讲）**
1. WSL2 一直报 `HCS_E_HYPERV_NOT_INSTALLED`：功能全 Enabled，但 BCD 里 **`hypervisorlaunchtype` = Off** → 提权 `bcdedit /set hypervisorlaunchtype auto` + 重启才解决；
2. PowerShell 5.1 读**无 BOM 的 UTF-8 带中文脚本**会按 ANSI 解码，直接语法崩溃 → 脚本一律纯 ASCII 或存 BOM；
3. `Start-Process` 起的 Streamlit 会随调用命令的进程树被回收 → 改用 **WMI `Win32_Process.Create`** 与调用方脱钩；
4. Docker Hub 直连被 DNS 污染（解析到 `100.49.158.130`）→ 需要走代理或镜像源（**当前未解决，别在面试里说 Docker 部分已跑通**）。
5. **端口 8000 上"启动成功"却访问不到 —— 健康检查不能只看状态码**（这个坑最值得讲）：
   本机 8000 被打印控件 C-Lodop（`CLodopPrint32.exe`，开机自启）绑在 `0.0.0.0:8000` 上。
   Windows 允许我们再绑一个更具体的 `127.0.0.1:8000`，于是 uvicorn **照常打印"Uvicorn running on 127.0.0.1:8000"**，
   但发往 `127.0.0.1:8000` 的请求全被那条通配 socket 抢走 —— `/docs` 打开是打印控件的欢迎页，
   `/health` 还返回 **HTTP 200 + HTML**。我原来的启动脚本只判断"端口在不在监听"，
   于是报 `api already listening - skipped`，又拿着那个 200 宣布成功。
   - 修法：换到 8010，并把健康检查改成**校验响应体**（`/health` 必须能解析成 JSON 且 `status=ok`）；
     启动前先查端口占用者，是别人就**拒绝启动并点名**，最后不健康就 `exit 1` 说"不要演示"。
   - **面试价值**：这是"探活"和"看起来活着"的区别。生产上同理 —— 健康检查必须回答"我这个服务能不能干活"，
     而不是"这个端口有没有人在听"。只看状态码的探活会把 502/错误页/别人的服务全当成健康。

# Part 3 · 怎么把上面讲出来

## 3 分钟版（先讲结论，再讲证据）
1. **一句话定位**（15s）："这是一个销售经营分析系统：给一句自然语言问题，它自己决定查什么数据、做量价归因、输出带对账的经营结论。"
2. **一个真实结论**（40s）：直接讲 10→11 月那个案例（+15.92%，量效应 +202 万、价效应 −51 万，公众号价格压力更大）。
3. **技术内核**（60s）：量价三因子分解可精确加总 → 断言校验；Agent 只负责"理解问题"和"表达结论"，数字全部由代码算。
4. **工程证据**（45s）：手写 ReAct（不用框架）→ 压测 6 场景 → 抓到并修掉 2 个真 bug（死循环检测误伤合法重试、日期校验太松）。
5. **边界与下一步**（20s）：数据没有成本字段所以不做毛利；客户维度弱；下一步加异常检测 P/R 与报告数字对账。

## 10 分钟版（按 Part 2 的分层顺序展开）
数据层 → 分析层（分解数学）→ Agent 层（机制表）→ 压测层（失败模式 + 2 个 bug）→ 编排选型（为什么确定性 DAG）→ 工程与部署（踩坑）→ 评测（指标）→ 局限与规划。

## 讲述纪律
- **数字必须能被追问**：说"5/5 可复算"就要能说清怎么复算的；
- **不夸大**：Docker 部分没跑通就说"环境已就绪、compose 配置已校验通过，还没端到端起过"；
- **主动交代边界**：没有成本字段、没有同比、客户维度弱——**主动说是加分，被问出来是减分**。
