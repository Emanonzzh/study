### 防幻觉对账（按项目规矩，Agent 说的数字必须能复算）

对问题 3 的回答里引用的每个数字，逐条回数据库复算：

| 模型引用 | 数据库复算 | 结论 |
|---|---|---|
| 微信公众号 客单价 1106.61 → 1030.59 | 3,995,960.72/3,611 = 1106.61；4,772,645.42/4,631 = 1030.59 | ✅ |
| APP 客单价 890.89 → 848.74 | 与工具输出一致 | ✅ |
| web网站 营收 −10.72 万 | 648,637.56 → 541,457.70，Δ = −107,179.86 | ✅ |
| 淘宝 营收 −1.74 万，客单价 1022.29 → 834.77 | 167,655.20 → 150,257.70，Δ = −17,397.50；AOV 1022.29 → 834.77 | ✅ |
| "若客单价维持 10 月水平，本可多约 51 万" | 即 price_effect = −512,555.14 | ✅ 语义正确 |

> **结论：5/5 全部可复算，零幻觉。** 原因很清楚——所有数字都来自工具返回值，
> 模型从未自己算过（`monthly_trend` 连环比都替它算好了，并在 note 里写明"不要自己重算"）。

### 从轨迹里看到的 3 个可教事实（这才是本次最大收获）

**① 工具描述就是 prompt —— 写工具描述 = 做 prompt engineering。**
问题 2 只是问"涨了还是跌了"，模型却**直接调用了 `contribution_breakdown`**，而不是先查两次 `revenue` 再比较。
原因：它在工具描述里读到"回答'为什么涨/跌'"。
→ 实证了机制 #1：**模型的工具选择行为由描述文本决定，不是由你的意图决定。**
→ 推论：想让它少绕路，就改描述；想让它多步推理，就把描述写窄。这是可控杠杆。

**② 文本协议在强格式约束下是可行的。**
3/3 零格式错误 —— 说明"经典 ReAct 文本协议 + 严格格式说明"对 deepseek-chat 够用，
不一定非得上原生 function calling。（但见下：样本太小，且都是"单工具显然够用"的题。）

**③ "代码算数、模型解读"落地了，而且可验证。**
模型没有自己算 51 万，它引用的是工具算好的 `total_price_effect`。
→ 这是整个项目架构理念（LLM 负责理解与表达、代码负责精确计算）的**第一次实证**，而不是口号。

## 2026-09-14 · 里程碑 2：D2 压测（主动把失败模式逼出来）

### 动机
里程碑 1 的 3 题全对、**零失败模式** —— 那不是 Agent 好，是**题目太简单**。
没有失败模式的 Agent 报告是不真实的，也学不到东西。于是写了 `agent_lab/p1_stress.py`，6 个场景主动撞边界。

### 新增能力：故障注入钩子
给 `run_agent()` 加了 `tool_hook` 参数，可以在真实工具外包一层报错/延迟/空数据，
用来验证"模型能不能读懂错误并自我修正"。这是**可控实验**，不是碰运气。

合计 16,351 tokens。

### 压测抓出的两个真 bug（已修复并重跑验证）

**bug 1 · 死循环检测误伤合法重试**
- 根因：签名状态只存**计数**，没考虑"上一次是否以错误收场"。
- 修复：状态改为 `{count, last_error}`，**上一次以工具错误收场时放行一次重试**（`legit_retry`）。
- 验证（重跑 T3）：日志出现 `↻ 上一次以工具错误收场，放行本次重试` → 拿到 **10,910 单**，
  `repeat_action` 消失，**耗时 24.8s → 3.1s**。（延迟下降是因为模型不再走那串"要不要放弃"的长推理。）

**bug 2 · 日期校验太松（只校格式不校语义）**
- 根因：`\d{4}-\d{2}-\d{2}` 放过了 `2025-13-01`，MySQL 返回空值，模型被迫自己猜。
- 修复：加月份 01~12、日期 01~31、年份范围校验。
- 验证（重跑 T2）：工具直接报 `start_date 的月份必须在 01~12 之间，收到 '2025-13-01'`，
  模型如实转达并给出替代月份，**耗时 24.0s → 2.9s**。

> **这两条是本轮最有价值的产出**：不是"Agent 跑通了"，而是"我发现了自己写的机制里的缺陷，
> 定位根因、修掉、并用重跑数据证明修复有效"。这才是面试里能站住的东西。

## 2026-09-15 · 里程碑 3：异常检测 + 注入集 + P/R（D3/D4）

### 产出文件（销售项目 `agent_lab/`）
| 文件 | 内容 |
|---|---|
| `db.py` | 统一数据库连接（避免四个模块各写一遍连接参数） |
| `anomaly.py` | 异常检测：周内效应校正 + 日历校正 + MAD 稳健统计 + 脉冲/漂移两类 |
| `inject_anomalies.py` | 注入 6 个已知异常到副本表 `orders_injected`，产出 ground truth |
| `evaluate_anomaly.py` | 差分口径 + 事件化后处理的 P/R/F1 评测 |
| `eval/anomaly_report.md` / `.json` | 评测报告 |

### 走错的第一步（重要教训）
第一版检测器 = 日粒度 + 3 天窗口比中位数 + 30% 阈值 → **真实数据上检出 175 个"异常"，全是误报**。
根因：**日销售额有强周内效应**（周六比周一高 40% 是常态），拿 3 天窗口比就等于拿周六比周一。

修正两处，并**如实记录各自贡献**：
1. **整周对整周**比较（7 天窗口 vs 7 天窗口）→ 175 → **28**（主要功劳）
2. **同星期几基线**（脉冲检测的基线只看前后几周的同一个星期几）→ 28 → **22**
> 不能把功劳全算给第 2 条 —— 这种"哪一步真正起作用"的区分本身就是工程判断。

### 评测：第一版 P 只有 35%，原因不是检测器
严格一对一匹配下 P=35.29%、R=100%，11 个"误报"。逐条归因后：
**11 个误报全部落在注入事件区间内或前后几天** —— 它们是持续性异常的「进入点 / 内部点 / 恢复点」。
**这是评测方法的错，不是检测器的错**：一个持续型异常天然产生多个检出点，一对一匹配只认一次。
修正：加**事件化后处理**（同维度值、间隔 ≤7 天的检出合并为一个事件）→ P 升到 54.55%。

### 最终指标（真实可复现）
| 口径 | P | R | F1 | TP/FP/FN |
|---|---|---|---|---|
| **事件化后处理（主）** | **54.55%** | **100%** | **70.59%** | 6/5/0 |
| 严格一对一（对照） | 35.29% | 100% | 52.17% | 6/11/0 |
| 原始口径（含真实事件，偏悲观） | 15.79% | 100% | 27.27% | 6/32/0 |

- **6/6 注入事件全部检出**
- **差分误报中「与所有注入都无关」的：0 个** → 没有凭空乱报
- 干净基线表上检出 22 个**真实业务事件**（元旦三平台同时暴涨 +143%/+187%/+192%）—— 这是"噪声地板"

### 门槛取舍实验（min_orders 扫描）
min_orders = 10 / 30 / 50 指标几乎不变 —— 这是**差分口径的特性**：低样本量切片（web网站日单量约 20）
在干净表和注入表里会同时被检出、差分时相互抵消；提到 80 才开始漏检（日单量不足 80 的平台被整体挡掉）。
→ **门槛过高会伤查全率**，这就是"用数据支撑的取舍"。

### 面试能讲的三点
1. **先归因，别急着调参**：指标低时我先逐条归因误报，发现全是同一事件的多次检出 → 改的是评测方法而不是阈值。
2. **差分评测**：真实数据有真实业务事件，直接比对会把"元旦暴涨"算成误报 → 用干净基线做差分剔除噪声地板。
3. **诚实报数**：同时给严格口径和宽松口径，主动交代局限（只评了 platform 维度、匹配容差偏宽、**未做 FDR 多重比较校正**）。

## 2026-09-16 · 里程碑 4：经营报告生成 + 数字对账（D5）

### 核心设计：数字由代码产生，模型不碰数值
- 模板里**只有占位符**；所有数值在 Python 里算好后以**字符串**传给模板（模板无法"顺手算错"）
- 引入**授权数字清单**：报告里会出现的数字（含派生值：环比、异常数、拖累项个数）都必须先登记

### 两道对账 + 一道自测
| 环节 | 做法 | 结果 |
|---|---|---|
| ① 文本级对账 | 抽取报告里**每一个数字**，核对是否来自分析结果 | 88 个数字，**0 违规，100% 通过** |
| ①-b **对账器自测** | 故意注入假数字 `999,999.99`，确认能被抓到 | ✅ 已抓到 |
| ② 数据库级对账 | 头部 11 项指标**重新从 MySQL 复算**再比对 | **11/11 全部一致，Δ=0.0** |
| ③ LLM 文本对账 | 让 LLM 写结论，再对账它写的文本 | 抽取 0 个数字（它选择不写数字），**0 编造** |

> **①-b 是关键**：只有先证明"注入假数字会被抓"，"0 违规"才有意义 ——
> 否则可能只是对账器太宽松。这就是 test the test。

### 修掉的对账器自身 3 个 bug
1. 正则 lookbehind 把逗号当边界 → `-512,555.14` 被切成 `555.14`（负数/千分位解析错误）
2. 百分数口径混用 → 源里 `delta_share_pct = 55.9` 已是百分数，我却按"小数×100"去找
3. 派生值（环比、异常数、拖累项个数）没进授权清单 → 补进 `analysis` 作为**单一数据源**

### 报告里的真实结论（2025-10 → 2025-11）
- 实付额 8,728,115.07 → 10,117,593.28（**+15.92%**）；订单数 +23.15%；客单价 **-5.87%**
- 量价分解：量效应 +2,020,698.05、价效应 **-512,555.14**、交互项 -118,664.70，**加总校验 0.00**
- 贡献最大：微信公众号 +776,684.70（占 55.90%）；拖累最大：web网站 -107,179.86
- 本期日粒度异常 0 个（各日波动都在同星期几基线的正常范围内）—— 这是结论，不是漏检

### 面试能讲的一点
> "报告类系统最大的坑是**幻觉数字**。我的做法是：数字全部由代码算好、以字符串传给模板，模型只写不含数字的自然语言；
> 发布前两道对账——文本级抽取每个数字核对来源，数据库级把头部指标重新算一遍；
> 而且我对**对账器本身**做了自测：注入假数字必须被抓到，否则'0 违规'没有意义。"
